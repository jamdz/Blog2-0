Blog API 2.0

A RESTful blogging service built on Node.js, Express, and MongoDB — with user-owned posts, image uploads, and a separate admin layer for platform management.

  • Auth — JWT delivered as HTTP-only cookies for users and admins alike
  • Posts — full CRUD, scoped so users only touch their own content
  • Uploads — Multer-backed cover images on every post
  • Discovery — public listing, search, and category filtering
  • Roles — user / admin enforced via middleware
  • Admin tools — user inspection and cascade delete via transaction
01

Project description

Blog API 2.0 is a backend service for a blogging platform. Registered users create an account, log in, and manage their own blog posts — creating, updating, and deleting entries, each with an optional cover image. Anyone, logged in or not, can browse, search, and filter every published post through a set of public endpoints.

A separate admin role sits on top of the same authentication system. Admins log in through a dedicated auth flow and get access to platform-management tools: listing every user, inspecting what a specific user has posted, and removing a user together with all of their posts in one atomic transaction.

Installation instructions

Requires Node.js (v18+ recommended) and a MongoDB instance — local, or a hosted service such as MongoDB Atlas.

  1. Clone the repository

    git clone https://github.com/jamdz/Blog2-0.git
cd Blog2-0

  2. Install dependencies

    npm install

  3. Create your environment file

    Add a .env file in the project root — see Environment variables below.

  4. Run the server

    Development mode, restarts automatically on file changes:

    npm run dev

    Production mode:

    npm start

  5. Confirm it's running

    The server listens on port 3000. Visit http://localhost:3000/ for a welcome JSON message confirming the API is live.

NOTE

The uploads/ folder — where post cover images are stored — must exist at the project root. It's already included in this repo.

Environment variables

Create a .env file in the project root with the following keys:

VariableDescription
databaseURL MongoDB connection string — an Atlas mongodb+srv://... URI, or a local mongodb://localhost:27017/<db-name>
JWT_SECRET Secret key used to sign and verify JWTs. Use a long, random string in production

Example .env:

databaseURL=mongodb+srv://<username>:<password>@cluster.mongodb.net/blog2
JWT_SECRET=your_long_random_secret_here
WARNING

Never commit your real .env file.

The repo currently has a file named .gitIgnore — double-check the casing matches what Git expects on your OS, since Git treats .gitignore case-sensitively on Linux/macOS.

Authentication instructions

Authentication is JWT-based, delivered via HTTP-only cookies rather than Authorization headers, for both regular users and admins.

  1. Register or log in via POST /v1/api/users/register (or /login) for regular users, or POST /v1/api/admin/auth/login for admins.
  2. On success, the server signs a JWT — userId/email for users, id/role for admins — sets it as an httpOnly, sameSite: strict cookie named token, and also returns the raw token in the response body.
  3. On later requests to protected routes, the client automatically sends the token cookie. authMiddleware reads req.cookies.token, verifies it against JWT_SECRET, and attaches the decoded payload to req.user.
  4. Admin-only routes additionally pass through requireAdmin, which checks req.user.role === "admin" — this must run after authMiddleware.
  5. Token expiry: user tokens last 1 hour; admin tokens last 2 hours. Clients must log in again once expired.
  6. Logging out clears the token cookie via the respective /logout endpoint.

Testing with Postman / Insomnia

Make sure cookie handling is enabled for your environment so the token cookie set on login is sent on later requests. Without cookie support, grab the token from the login response body and attach it manually:

Cookie: token=<your_token>
